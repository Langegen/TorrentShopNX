# План оптимизации торрент-движка

Цели:
1. Максимальная скорость скачивания.
2. Максимальная стабильность.
3. Пока идёт скачивание, приложение работает нормально: обложки и скриншоты грузятся, новые раздачи добавляются в очередь без зависаний.
4. Ротация пиров: подключаться к как можно большему числу доступных пиров и держать самых быстрых.

План составлен по коду ветки `test` (коммит `bfa2d987a`). Ссылки на строки приблизительные.

### 1.2. Почему netloop тратит много CPU (это бьёт и по скорости, и по UI)

`request_scan()` вызывается после **каждого** события poll по сессии, для **каждой** uTP-сессии на каждой итерации и в upkeep каждые 125 мс. Внутри для каждого запрашиваемого блока (до 256 на сессию):

| # | Горячая точка | Сложность |
|---|---------------|-----------|
| C1 | `scan_next_block()`: 5 зон × 2 прохода × все части от playhead до `file_last_piece + 16`. Для каждой части вызываются `piece_priority()` и `bf_has_piece()`. | O(зоны × части) **на один блок**. Для файла 11 ГБ / 4 МБ это ~28 000 итераций на блок. |
| C2 | `next_block_in()` → `sess_has_req()`: линейный поиск по кольцу запросов сессии для каждого блока части. | O(nblocks × req_n) ≈ 256 × 256 |
| C3 | `active_healthy_reqs()`: обход всех сессий и всех их запросов. | O(MAX_SESS × req_n) |
| C4 | `aq_find()`: линейный поиск по 48 слотам, вызывается на каждый запрос и каждый ответ. | O(AQ_MAX) |
| C5 | `peer_is_seed()` / `peer_has_needed()`: проход по всем частям файла для каждой сессии на каждом upkeep. | O(MAX_SESS × части) × 8 раз/с |
| C6 | `take_peer()`: пул 2048 × проверка IP по 64 сессиям, **под `t->lock`**, до 12 раз за тик. `add_peers_src()`: дедупликация O(n × peer_count) под тем же локом. | до ~1,5 млн сравнений/тик под локом |
| C7 | writer опрашивает очередь каждые 2 мс (`svcSleepThread`), reader опрашивает готовность части каждые 20 мс. | Холостые пробуждения; к каждой части добавляется в среднем ~10 мс задержки. |
| C8 | Под `t->lock` делаются большие `memcpy`: `aq_piece_read()` и `cache_piece_read()` из буфера writer'а. | netloop ждёт копирования мегабайтов. |

### 1.3. Что ограничивает скорость

| # | Проблема | Где |
|---|----------|-----|
| S1 | **Окно планировщика фиксировано по числу частей** (25–44 части, ≤320 МБ). Пока окно задано, все части вне зон получают приоритет 0, и пиры с запасом конвейера простаивают. Окно не зависит от измеренной скорости. | `custom_engine_scheduler.h:63-105`, `torrentfs.c:1547-1587` |

Повторяется при каждой смене части и на каждом `on_stall`. | `custom_engine_scheduler.cpp:195-218`, `torrentfs.c:3836-3861` |

| S4 | Для не-игровых файлов (`highThroughputFileConfig`) используется тот же последовательный стриминг через RAM-окно, хотя файл пишется на SD целиком. Выбор частей по порядку ухудшает доступность частей в бедных роях: rarest-first здесь подошёл бы лучше. | `custom_engine_backend.cpp:146-158` |
| S5 | Буферы сокетов выдаются всем одинаково, 256 КБ после handshake, независимо от скорости пира. Медленные пиры занимают пул, который нужен быстрым и HTTP. | `bt_peer.c:662-698` |
| S6 | Входящее соединение при заполненных слотах просто закрывается, хотя входящие пиры (из-за NAT) часто самые ценные. | `torrentfs.c:2560-2566` |

### 1.4. Ротация пиров

Что сейчас:
- Новые пиры не набираются, если `live ≥ 50` (`DIAL_STOP_LIVE`) и `unchoked ≥ 24`. **Медленные пиры не заменяются**: какие пиры подключились первыми, с теми рой и остаётся.
- Отключаются только: (а) пиры, которые держат нас в choke ≥ 45 с без данных, и то лишь при `pool_rich`; (б) пиры со stall-страйками (25 с без блоков). Пир, который отдаёт 20 КБ/с, живёт вечно.
- `peer_eval_score()` учитывает только бинарный признак `peer_ok`, источник и число ошибок. **Истории скорости нет**: пир, отдававший 5 МБ/с, после разрыва ничем не лучше пира с 30 КБ/с.
- Дедупликация в пуле **только по IP** (`add_peers_src`), плюс запрет второй сессии на тот же IP (`take_peer`). Несколько клиентов за одним NAT или CGNAT (разные порты) теряются.
- Дозвон: таймаут 2 с; при первом таймауте адрес паркуется на 60 с. На Wi-Fi с потерей SYN живой пир может не успеть.
- В пуле 2048 адресов, поиск линейный под локом (C6).
- Повторный анонс фиксирован: раз в 15 мин или раз в 60 с при голодании. Нет логики «кандидаты закончились, нужны свежие адреса».

## 2. План работ

Порядок фаз выбран так, чтобы сначала получить измерения, затем быстро разблокировать UI и только потом трогать планировщик и ротацию.

### Фаза 0. Метрики и базовая линия (P0, 1–2 дня)

Без цифр нельзя доказать, что изменения помогли.

1. Раз в 5 с писать в лог строку `perf`:
   - время итерации netloop: p50/p95/max;
   - число вызовов `request_scan` в секунду;
   - время кадра UI: p95/max (`torrentfs_hb_ui` уже есть, нужно агрегировать);
   - скорость скачивания: полезная и дубликаты в %;
   - `live`, `unchoked`, `connecting`, сколько пиров дают 80 % трафика;
   - число ENOBUFS и `sock_fail`;
   - задержка загрузки обложки: от `enqueue` до `sync`.
2. Метрики событий: время от нажатия «Скачать» до появления элемента в очереди и до первого байта; время удержания `queue_mutex_` (max за интервал).
3. Сценарии прогона (Switch и `pctest`):
   - A — хороший рой (50+ сидов, ≥8 ГБ);
   - B — бедный рой (2–5 сидов);
   - C — во время A прокручивать каталог со 100+ обложками и открывать скриншоты;
   - D — во время A добавить в очередь 5 раздач подряд (magnet);
   - E — параллельно зонд и загрузка.
4. Записать базовые значения в этот документ (таблица «до/после»).

**Критерий:** в логе есть `perf`-строки, сняты значения для сценариев A–E.

### Фаза 1. Разблокировка UI (P0, быстрые победы)

1. **Ядра и приоритеты потоков** (U1):
   - ядро 0: только UI (borealis) и, при необходимости, лёгкие потоки;
   - ядро 2: netloop (приоритет `0x2C`, то есть не выше UI), discovery, DHT, listener, UPnP, потоки анонса (`0x2E`);
   - ядро 1: writer/SHA-1 (`0x2D`), поток установки (уже там), воркеры обложек и декодирование `stbi` (`0x2D`);
   - collector инсталлятора: с ядра 0 / `0x20` перенести на ядро 2 / `0x2C`;
   - в режиме апплета проверить доступную маску ядер (`svcGetInfo(InfoType_CoreMask)`) и откатываться на `-2`, если ядро недоступно;
   - вынести константы ядер и приоритетов в одно место (`engine/thread_cfg.h`).
2. **Вынести блокирующую работу из-под `queue_mutex_`** (U2):
   - `trackProgress()`: под локом только снимать снимок нужных полей и применять результаты; `probeFiles`, `startHybridInstall` → `open`, `getTorrentFiles` выполнять вне лока;
   - `startHybridInstall` при отсутствии файлов не зондирует синхронно, а запускает асинхронную задачу (`std::async` / свой воркер) и переводит элемент в `StreamPreparing`; результат подхватывается на следующем тике;
   - `addToQueue()` и UI-методы должны брать лок на микросекунды. Проверить через метрику удержания лока из фазы 0.
3. **Асинхронный логгер** (U4, U5): общий кольцевой буфер (например, 256 КБ) и отдельный поток на ядре 2 с низким приоритетом. Файл держится открытым, сброс раз в 1 с или при WARN/ERR. И `util::logLine`, и `engine_log` пишут в кольцо без IO. Если кольцо переполнено, строки отбрасываются со счётчиком `dropped`. По умолчанию engine-лог на уровне WARN, плюс агрегированные `perf`/`SWARM`; построчные INFO (`piece verified`, `handshake ok`, `added peers`) переводятся в DEBUG.
4. **Анонсы без глобального мьютекса** (U3):
   - убрать `s_announce_mtx`, сделать общий пул анонс-воркеров (2–3 потока на Switch) с очередью задач (торрент, трекер);
   - не ждать всех трекеров: пиры приходят через callback, discovery не блокируется;
   - метаданные новой раздачи ставятся в начало очереди;
   - кэш DNS (host → IP, TTL 10 мин) и отрицательный кэш для трекеров с DNS-ошибкой (уже есть `tracker_is_on_cooldown`, его нужно распространить на DNS);
   - семафор BSD-сессий из п. 6 ограничивает число одновременных воркеров.
5. **Потокобезопасный реестр движка** (U7): мьютекс на `tsnx_engine` и счётчик ссылок на `tsnx_torrent`/`torrentfs`. `remove_torrent` помечает слот на удаление и закрывает его, когда последняя ссылка отпущена. Убрать `probe_mtx_` как сериализацию «одна раздача за раз»: зонды разных хешей идут параллельно (ограничены пулом из п. 4).
6. **Бюджет BSD-сессий и памяти сокетов** (U6):
   - глобальный счётный семафор блокирующих сессий: движок ≤ 10 (meta-воркеры 8 → 4–6, анонсы 2–3), **резерв 4 для HTTP/обложек**, они никогда его не ждут;
   - счётчик ENOBUFS в `perf`; при ENOBUFS снижать лимит сессий движка на 10 % на 30 с.
7. **Снимок статуса** (U8): netloop раз в 250 мс публикует `torrentfs_snapshot` (progress, скорость EWMA, live/seeds/known, dht nodes) через seqlock или двойной буфер. Все геттеры (`get_torrents`, `status`, `downloadSpeedKBps`) читают снимок без `t->lock`. Скорость считается в netloop, а не в геттере. Добавить `tsnx_engine_get_torrent(hash, &item)`, убрать лимит 8.
8. **Обложки** (U9): после п. 1 и 6 убрать задержку 15 мс, на Switch увеличить число воркеров до 3. Логирование каждой обложки перевести в DEBUG.

**Критерии:**
- сценарий C: p95 кадра UI ≤ 20 мс, max ≤ 50 мс, обложка из сети ≤ 1,5 с (p95);
- сценарий D: каждая раздача появляется в очереди ≤ 200 мс после нажатия, `queue_mutex_` удерживается ≤ 5 мс;
- скорость в сценарии A не падает относительно базы.

### Фаза 2. CPU сетевого цикла (P0)

1. **Список кандидатов вместо полного скана** (C1): при изменении playhead, зон или статуса части (dirty-флаг) netloop перестраивает массив `wanted[]` из частей с приоритетом > 0, отсортированный по (зона, индекс). Его размер равен размеру окна, это десятки или сотни частей, а не тысячи. `scan_next_block` идёт по `wanted[]` с курсором, проходы 1 и 2 остаются.
2. **O(1) учёт запросов** (C2, C3): в `aq_entry` добавить `uint64_t req_mask[nblocks]` (бит на сессию, MAX_SESS ≤ 64) и `req_ts`. `sess_has_req` становится проверкой бита, `active_healthy_reqs` — `popcount` по маске с исключением «плохих» сессий (маска сессий со страйками).
3. **Индекс piece → aq** (C4): `int8_t aq_of_piece[piece_count]`, обновляется в `aq_alloc` и `piece_full`.
4. **Кэш состояния пира** (C5): при BITFIELD/HAVE вести у сессии `have_in_file` (счётчик частей файла) → `is_seed = have_in_file == file_pieces`. `peer_has_needed` проверяет по `wanted[]`, а не по всем частям.
5. **Пул пиров с хеш-индексом** (C6): хеш-таблица `ip:port → pidx` (открытая адресация, 4096 слотов) для дедупликации за O(1); множество активных IP для `take_peer`; очереди готовых кандидатов по корзинам score (см. фазу 4), чтобы не сканировать 2048 записей.
6. **Батчинг `request_scan`**: дозапрашивать, только когда `req_n < 0.75 × depth` или пришёл UNCHOKE / новые HAVE; для uTP-сессий только после фактического приёма данных.
7. **Пробуждения по событию** (C7): writer ждёт на `CondVar`/`UEvent`, netloop сигналит в `piece_full`; reader ждёт на `CondVar`, writer сигналит после `PIECE_DONE` (таймаут ожидания 200 мс сохраняется для watchdog и stall-логики).
8. **Копирование без `t->lock`** (C8): у буфера части счётчик ссылок (pin); reader пинит буфер под локом, копирует без лока, затем отпускает.

**Критерии:** при 64 сессиях и 10 МБ/с p95 итерации netloop ≤ 2 мс; число вызовов `scan_next_block` на блок ≈ 1; загрузка ядра netloop < 40 % при 10 МБ/с.

### Фаза 3. Скорость скачивания (P1)

1. **Атомарное окно зон** (S2): новый API `tsnx_engine_set_window(hash, const tsnx_zone_range *ranges, int n)`. Движок хранит до 8 диапазонов в двойном буфере и переключает указатель атомарно; `piece_priority()` считает зону по диапазонам, массив `piece_zone[]` не нужен. Планировщик формирует все диапазоны за один вызов. Ускорение на slow-peer (boost) — часть того же набора.
2. **Адаптивное окно** (S1): размер окна в байтах = `clamp(rate_ewma × 8 с, 64 МБ, 0.75 × RAM-бюджета)`, плюс нижняя граница «сумма `nominal_depth` всех unchoked-сессий × 1,5». Планировщик пересчитывает окно раз в секунду. В stall-режиме окно не сужается до 2 частей: сужается только зона Normal, Critical/Urgent расширяются на 1–2 части.
3. **Общий бюджет сессий** (S3): глобальный лимит соединений, например 80 на всё приложение. Активная установка получает ≥ 75 %, зонд метаданных и фоновые торренты — остаток. В torrentfs передаётся `max_sess_now`, dialer его соблюдает. Долгосрочно можно сделать один netloop на все торренты (общий poll), это отдельная задача.
4. **Адаптивные буферы сокетов** (S5): после handshake ставится `SO_RCVBUF = 64 КБ`. Если скорость пира держится > 256 КБ/с 5 с, буфер поднимается до 256 КБ, если > 1 МБ/с — до 512 КБ (с откатом при ошибке). Суммарный бюджет RX-буферов движка ≤ 50 % пула сокетов.
5. **Режим «файл целиком»** (S4): для не-игровых файлов писать проверенные части прямо в целевой файл (или чанки на FAT32) по rarest-first внутри выбранных файлов, без RAM-окна и без последовательного чтения через `read()`. Для бедных роёв это заметно поднимает скорость. Отдельная задача, начинать после фаз 1–2.
6. **Входящие при заполненных слотах** (S6): принимать соединение и вытеснять худшую сессию по правилам ротации (фаза 4), если новый пир не в бане.
7. **Отдача (reciprocity)**: проверить, что в RAM-режиме мы реально отдаём (метрика `st_up_bytes`); при наличии частей держать 4–8 слотов unchoke. Это поднимает нас в tit-for-tat у личеров.
8. **Дубликаты**: целевой уровень `dup_bytes` < 3 % в хорошем рое. Если выше, ограничить hedging (`max_dup = 4`) только Critical-частью и endgame, а не `zone ≤ 2`.

**Критерии:** сценарий A — устойчивая скорость не ниже PC-клиента в той же сети (или ≥ 90 % канала Wi-Fi); сценарий B — нет простоев > 30 с при наличии хотя бы одного живого сида.

### Фаза 4. Ротация пиров (P1)

Цель: перебрать как можно больше доступных пиров и держать соединения с самыми быстрыми.

1. **Запись о пире в пуле**: добавить `best_rate`, `last_rate`, `bytes_total`, `last_connected`, `conn_count`, `snub_count`. Новый score:
   `score = 3000·[был быстрым ≥ 1 МБ/с] + log2(best_rate) · 100 + источник (tracker 500 / PEX 400 / incoming 450 / DHT 100) + свежесть − ошибки · 40`.
2. **Очередь дозвона по корзинам**:
   - (1) проверенно быстрые;
   - (2) peer_ok;
   - (3) свежие tracker/PEX/incoming;
   - (4) не опробованные DHT;
   - (5) повторы после ошибок.

   Берём из старшей непустой корзины, но каждый 4-й дозвон — из (3)/(4), чтобы постоянно открывать новых пиров.
3. **Регулярная ротация медленных (turnover)**: раз в 30 с, если `live ≥ 0.9 × лимита` и в пуле есть готовые кандидаты:
   - ранжировать сессии по полезной скорости за последние 30–60 с;
   - отключить K = max(2, 10 % сессий) худших. Не трогать: сессии моложе 60 с (разгон), единственного держателя нужной части, пира, который сейчас качает Critical-часть, сида в бедном рое (`live ≤ 4`);
   - пир, отключённый за медленность, получает backoff 10 мин (не бан), чтобы освободить место непроверенным;
   - на их место сразу набираются кандидаты из очереди п. 2.
4. **Запас дозвона**: держать `connecting` до 16 слотов даже при полном лимите, чтобы новые пиры проверялись до вытеснения старых («сначала подключить, потом выгнать»).
5. **Snub-детектор**: unchoked и есть запросы, но 15 с ни одного блока → `snubbed`. Его глубина конвейера `REQ_MIN`, блоки уходят другим, и он первый кандидат на ротацию (быстрее, чем `STALL_SECS = 25` и 3 страйка).
6. **Быстрые возвращаются быстро**: если пир с `best_rate ≥ 1 МБ/с` отвалился по сетевой ошибке, backoff 5 с без экспоненты, первые 3 раза.
7. **Ключ `ip:port`**: дедупликация по паре, до 2 сессий на один IP (разные порты), чтобы не терять клиентов за CGNAT/NAT.
8. **Дозвон**: базовый таймаут 3 с; при `PEER_FAIL_TIMEOUT` ещё одна попытка через 30 с с таймаутом 5 с, потом обычная парковка. uTP-попытка после неудачного TCP разрешена и при `few_peers` (сейчас uTP отключается как раз тогда, когда NAT-пиры важнее всего).
9. **Свежие адреса**: если в пуле не осталось готовых кандидатов из корзин (1)–(4), внеочередной анонс с соблюдением `min interval` трекера и `numwant=200`, ускоренный DHT-поиск и PEX-запросы раз в 15 с. Не повторять «event=started».
10. **Метрики ротации** в `perf`: сколько ротировано, средняя скорость отключённых и новых, доля трафика топ-10 пиров, пиров опробовано за сессию.

**Критерии:** в сценарии A через 5 мин средняя скорость на сессию растёт (медленные заменены); опробовано ≥ 70 % достижимых адресов пула; в сценарии B ни один живой сид не отключён ротацией.

### Фаза 5. Стабильность (P1–P2)

1. **Память под части**: выделять буферы частей одним блоком при открытии (`n_aq × piece_len` с понижением при неудаче) вместо `malloc` 4–16 МБ на часть. Это убирает фрагментацию кучи при долгих загрузках.
2. **Строгая проверка**: оставить `strict_verify = 1` для установки (сейчас это так). Для нестрогого режима (если понадобится) нужен откат: при SHA-ошибке части, уже отданной читателю, инсталлер должен узнать об этом и перечитать.
3. **Гонки reader/netloop**: `piece_ready()` и `aq_find()` из потока reader без лока — после индекса из фазы 2 (п. 3) читать через атомарный `aq_of_piece` и `status`.
4. **Мелочи**: `static u64 last_dup_dbg` общий для всех торрентов → поле структуры; `tsnx_engine_set_file_wanted()` сейчас ни на что не влияет — либо реализовать (исключить части ненужных файлов из `wanted[]`), либо убрать из API; `get_torrents(…, 8)` → поиск по хешу.
5. **Сторожевые проверки**: при stall > 45 с reader возвращает 0 (уже есть). Backend должен различать «нет пиров» и «нет данных в окне» и в первом случае вызывать `announce_now` и расширять ротацию, а не просто ждать.
6. **Регрессионные тесты в `pctest`**: окно зон (атомарность), ротация (моделируемые пиры с разной скоростью), реестр (параллельные add/remove/get из N потоков под TSan на PC).

## 4. Статус выполнения

### Сделано: фаза 0 (метрики)

Раз в 5 с (при простое раз в 60 с) в лог пишутся две строки:

```
[perf] net loop_us p50=… p95=… max=… iters=… scans/s=… picks/s=… rate=…KB/s dup=…% live=… unchoked=… connecting=… pool=… sock_fail+… enobufs+… timeouts+…
[perf] ui window=5s frames=… fps=… frame_ms p50=… p95=… max=… jank33=… freeze100=… | qlock track n=… hold_avg=… hold_max=… wait_max=… | qlock add … | img net n=… p50=… p95=… max=… disk n=… p95=… max=…
```

- `net` (engine.log, по строке на каждый открытый торрент): `loop_us` — CPU-время одной итерации netloop без ожидания в poll; `scans/s` — вызовы `request_scan`; `picks/s` — вызовы `scan_next_block` (по одному на каждый запрошенный блок); `rate` — полезная скорость за окно; `dup` — доля дубликатов; `enobufs` — отказы сокетов из-за исчерпания BSD-пула.
- `ui` (log.txt и engine.log): время кадра (`jank33` — кадры ≥ 33 мс, `freeze100` — ≥ 100 мс); `qlock track` — сколько поток прогресса держал мьютекс очереди и сколько ждал его; `qlock add` — сколько UI ждал мьютекс при добавлении раздачи; `img` — время от запроса обложки до готовности к показу (сеть / кэш на SD).
- Код: `source/engine/perf_hist.h` (гистограмма p50/p95), `perf_emit()` в `torrentfs.c`, `source/utils/perf_stats.{h,cpp}`.

### Сделано: фаза 1, пп. 1–3

1. **Ядра и приоритеты** (`source/engine/thread_cfg.h`):
   - ядро 0 — только UI;
   - ядро 1 — writer/SHA-1, collector и поток установки, воркеры обложек, логгеры;
   - ядро 2 — netloop (0x2B), discovery, DHT, анонсы, listener, UPnP, meta-воркеры, поток прогресса;
   - доступность ядер проверяется по `InfoType_CoreMask`. Если ядро недоступно, поток остаётся на ядре по умолчанию (это ядро UI) и получает приоритет **ниже** UI (0x2D);
   - раньше netloop (0x2B) и collector (0x20) работали на ядре UI с приоритетом выше UI.
2. **Мьютекс очереди**:
   - `probeFiles()` (получение метаданных) в `startHybridInstall()` идёт в отдельном потоке (`startLocalProbe`); пока зонд не готов, функция возвращает «ещё не начато», и поток прогресса проверяет результат на следующем тике (раз в 100 мс);
   - при ошибке зонда повтор через 5 с вместо немедленного;
   - опрос списка торрентов движка выполняется до захвата мьютекса;
   - удаление торрента (ждёт завершения его потоков) из `trackProgress` откладывается и выполняется тем же потоком прогресса сразу после отпускания мьютекса. Перед удалением проверяется, что раздача не была снова взята в работу. Ручные отмена и удаление по-прежнему удаляют синхронно.
3. **Асинхронный лог**:
   - `engine_log`: кольцевой буфер 256 КБ и поток-писатель на ядре 1; запись на SD пачками, `fflush` раз в 500 мс; WARN/ERR будят писателя сразу; при переполнении строки отбрасываются со счётчиком `[log] dropped N lines`;
   - `util::logLine`: буфер в памяти и поток-писатель. Файл по-прежнему открывается и закрывается на каждую пачку (не держится открытым), но не чаще раза в 500 мс вместо раза на каждую строку;
   - перед `_exit` логи сбрасываются (`engine_log_flush`, `util::logClose`);
   - строки `[writer] piece … verified` (по одной на часть) переведены в DEBUG; убраны строки на каждую обложку (`HTTP 200 OK`, `loaded thumbnail from disk`), их заменила метрика `img`.

### Новые находки

- **Подбор блоков дорожает с размером файла** (подтверждает C1): loopback 2 ГБ — 784 МБ/с, 8 ГБ — 338 МБ/с, p95 итерации netloop до 10–14 мс на PC при одном пире, `picks/s` ≈ 24–38 тыс. На Switch эффект будет сильнее (CPU слабее).
- **Падение при остановке движка — исправлено.** Причина оказалась не в остановке, а в переполнении очереди writer уже во время загрузки (см. «Исправленные ошибки»).

### Сделано: фаза 1, пп. 4–8

4. **Анонсы без глобального мьютекса** (`torrent_meta.c`): раунды анонса больше не ждут друг друга. Каждый раунд разбирает свой список трекеров пулом воркеров: до 3 на Switch, причём вызывающий поток работает сам, так что раунд всегда движется. Общее число дополнительных потоков анонса по всему процессу ограничено `ANNOUNCE_GLOBAL_MAX` (3 на Switch). Раньше трекеры после второго опрашивались строго по очереди. Таблица остывания трекеров получила свой лок (раньше её неявно защищал глобальный мьютекс). Проверено на PC: раунд из 5 трекеров укладывается примерно в 1 с — время самого медленного трекера, а не сумму.
5. **Потокобезопасный реестр движка** (`engine.c`):
   - один лок `g_reg` на состояние слотов и указатель `fs`; короткие вызовы (статус, зоны, пиры, пауза) выполняются под ним;
   - долгие вызовы (блокирующее чтение, `select_file`) учитываются счётчиками `fs_users` и `holders`; удаление и замена `fs` ждут их обнуления и закрывают `fs` вне лока;
   - добавление резервирует слот, невидимый для поиска, пока не придут метаданные; если тот же торрент добавили параллельно, используется существующий;
   - listener получил атомарную маршрутизацию: поиск торрента и постановка сокета в очередь под одним локом (раньше он получал голый указатель на `fs`);
   - колбэк DHT: `dht_background_remove()` ждёт колбэки, которые уже выполняются (раньше колбэк мог писать в освобождённый `torrentfs`);
   - поток discovery спит шагами по 50 мс, поэтому удаление торрента занимает ~0,1 с вместо ~0,65 с.
6. **BSD-сессии** (частично): на Switch число воркеров получения метаданных уменьшено с 8 до 5, чтобы компенсировать параллельные анонсы; пиковое число сокетов движка не выросло. Полноценный семафор блокирующих сессий с резервом для UI и адаптация к ENOBUFS — не сделаны.
7. **Снимок статуса** (`torrentfs.c`): сетевой цикл раз в 125 мс публикует снимок (список пиров, число сидов, `claiming`/`idle`), и геттеры читают только его. Раньше `get_peers` и `seed_count` читали приватное состояние сессий из чужих потоков, включая `bitfield`, который сетевой цикл освобождает. «Сид ли пир» теперь проверяется за O(1) по счётчику частей (`have_in_file`, обновляется на BITFIELD/HAVE). Новый `tsnx_engine_get_torrent(hash)`; убран лимит в 8 торрентов в backend и менеджере загрузок (`TSNX_MAX_TORRENTS` = 32).
8. **Обложки**: убрана искусственная пауза 15 мс перед каждой загрузкой во время скачивания. Число воркеров оставлено 2, поднимать его до появления семафора из п. 6 рискованно.

### Исправленные ошибки

- **Переполнение очереди writer → повреждение памяти.** Очередь рассчитана на 50 задач, а «одна задача на слот» не выполнялось: слот сборки получает новый буфер, как только старый ушёл в очередь. Если writer (SHA-1) отставал от сети, очередь росла: на PC — до 150+ задач, кольцо перезаписывало само себя, задачи выполнялись дважды, куча портилась; память росла без предела (150 × 4 МБ). Теперь новую часть можно открыть, только если «задачи в очереди + активные части» меньше вместимости (обратное давление на сеть); плюс защитная проверка в `piece_full()` и счётчик `wq_full` в `[perf] net`.
- **Повторное закрытие uTP-сокета при выходе** (`utp_nb_exit`): закрывались и сессии, уже закрытые через `utp_nb_close()`. libutp это запрещает (assert на PC; с `NDEBUG` на Switch — повторный FIN по сокету в состоянии закрытия).
- **Пустое чтение в нестрогом режиме**: читатель искал непроверенную часть двумя отдельными захватами лока (очередь writer, затем слот сборки) и мог не найти её ни там, ни там, если сеть успела завершить часть между проверками. Теперь обе проверки идут под одним захватом. В приложении включён строгий режим, и этот путь не используется, но тестовый прогон на 4 ГБ на нём падал.
- **Утечка сокетов** из очереди входящих соединений при закрытии торрента.

### Проверка (пп. 4–8 и исправления)

- `pctest`: офлайн-тесты, `test_mechanisms` (4/4), `test_engine_perf` 4 ГБ — 11 из 11 прогонов без падений, данные совпадают, код выхода 0 (до исправлений — падение в каждом прогоне от 512 МБ).
- Новый `pctest/test_registry.cpp` — стресс реестра: торрент 15 с подряд удаляется и добавляется заново (40+ циклов), параллельно читатель проверяет каждый байт и два потока гоняют API статуса, зон и пиров (~5–8 млн раундов). Новая версия: 3 из 3 прогонов без расхождений. Старый код на том же тесте: 3 из 3 падений (access violation).

### Сделано: фаза 2 (CPU сетевого цикла)

1. **Список кандидатов** (C1): части с ненулевым приоритетом, сгруппированные по зонам, хранятся в списке. Он перестраивается, только когда меняются позиция чтения, зоны планировщика (счётчик `zone_gen`) или файл; на практике 50–100 раз в секунду, примерно раз на новую часть. «Заблокированная» часть читателя меняется на каждое чтение, поэтому в список не входит и всегда проверяется первой в зоне 1. Раньше приоритет **каждой** части файла пересчитывался при подборе каждого блока.
2. **Маска запросов** (C2, C3): у слота сборки на каждый блок — битовая маска сессий, которые его запросили. Она ведётся синхронно с кольцами запросов. Проверка «эта сессия уже запросила блок» стала O(1). Отмена копий пришедшего блока обходит только держателей из маски, а не все сессии × все их запросы.
3. **Индекс часть → слот** (C4): `aq_find()` за O(1) вместо прохода по 48 слотам.
4. **Батчинг дозапросов**: после приёма данных кольцо пополняется, только когда освободилось `max(4, depth/8)` мест. Если читатель ждёт часть, дозапрос идёт сразу. Плановый проход раз в 125 мс — без изменений.
5. **Пробуждения по событию** (C7): writer ждёт на условной переменной вместо опроса каждые 2 мс; читатель просыпается сразу, как только часть проверена, вместо опроса каждые 20 мс.
6. **Пул пиров** (C6): хеш-индекс IP → слот (дедупликация за O(1) вместо прохода по 2048 записям на каждый адрес); при заполненном пуле вытесняется худшая из 64 записей с бегущего курсора; при дозвоне проверка «уже подключены к этому IP» идёт только по входящим сессиям, потому что исходящие и так помечают свою запись занятой.
7. C5 (`peer_is_seed` за O(1)) сделан ещё в фазе 1, п. 7. C8 (копирование без `t->lock`) не делался: в строгом режиме, который использует приложение, читатель копирует из RAM-окна под `cache_lock`, а не под `t->lock`.

### Сделано: фаза 3 (скорость)

Главное открытие фазы — **медленные пиры не добавляли скорость, а отнимали её**. На тесте «1 быстрый + 2 медленных сида» загрузка шла в 6 раз медленнее, чем с одним быстрым сидом (62 против 384 МБ/с). Планировщик раздавал медленным пирам блоки тех же частей, которые читатель ждал прямо сейчас. Часть не завершалась, пока медленный пир не отдаст свой блок, а дублирующий запрос к быстрому пиру уходил только через 1 с (для фоновых частей — через 2,5 с). Это напрямую относится к пункту «держать самых быстрых пиров».

1. **Планирование с учётом скорости** (`torrentfs.c`, по мотивам speed classes в libtorrent):
   - пир, отдающий меньше 25 % от лучшего (после 512 КБ данных), или пир со stall-страйками считается медленным, если есть хотя бы один быстрый; обратно в быстрые он возвращается выше 40 % (гистерезис);
   - медленный пир не берёт блоки зон 1–2 (ближайшие части). Он качает **свою отдельную часть** из дальнего конца окна и продолжает её до конца; если открыть новую нельзя, помогает в самых дальних активных частях;
   - если блок нужной сейчас части держат только медленные пиры, быстрый пир запрашивает его сразу, не дожидаясь таймаута;
   - **оценка скорости по времени обслуживания**: на каждый пришедший блок считается время от момента «пир мог начать этот блок» (позже из двух: его запрос и приход предыдущего блока) до прихода. Простой не засчитывается. Прежние счётчики (EWMA и средняя за время с запросами) обновлялись раз в 125 мс и только при непустой очереди. Быстрый сид успевал выкачать всё окно и ждал читателя, поэтому его скорость читалась как 0, его записывали в медленные, и он так и оставался без работы.
2. **Атомарное окно зон** (S2): `tsnx_engine_set_window()` / `torrentfs_set_zones()` заменяют все зоны за один захват лока и один `zone_gen`. Планировщик (`CustomEngineScheduler::apply_zones`) использует его вместо «очистить + 5–6 вызовов».
3. **Окно в байтах для мелких частей** (S1): для частей меньше 4 МБ зона Normal увеличивается так, чтобы окно было не меньше 128 МБ (раньше 44 части, то есть 44 МБ при частях 1 МБ).
4. **Входящие при заполненных слотах** (S6): вместо закрытия входящего соединения вытесняется незавершённый исходящий дозвон, затем пир, который 30 с держит нас в choke без данных, затем самый медленный пир старше 60 с. Сиды в бедном рое (≤ 4 живых сессий) не вытесняются.
5. `[perf] net` дополнен полями `fast=`/`slow=` (классы скорости), `aq=` (активные части), `rb=`/`rb_st=` (часть, которую ждёт читатель, и её состояние).

Не сделано в фазе 3: общий бюджет сессий на несколько торрентов (S3: в приложении одновременно качается одна раздача), адаптивные буферы сокетов (S5: на localhost не проверить, нужен реальный рой), режим «файл целиком» (S4, отдельная задача).

### Сделано: фаза 4 (ротация пиров)

Раньше движок держал тех пиров, которые подключились первыми: при 50 живых сессиях дозвон прекращался, и пир на 20 КБ/с занимал слот до конца загрузки.

1. **Турнир** (`turnover_tick`):
   - если сессий почти столько, сколько нужно, и в пуле есть готовые адреса, открывается окно: разрешено дозвонить до 4 кандидатов сверх цели;
   - окно закрывается, когда все новички оценены (отдали 512 КБ) или кончилась проба (60 с);
   - затем лишние сессии отсекаются по одной за тик: уходит худшая по оценке скорости, старая или новая; за окно — не больше 4;
   - окна открываются каждые 30 с, а пока в наборе есть медленные — каждые 10 с.
2. **Вытеснение без потерь:** долгую паузу (10 мин) и штраф в пуле получает только действительно медленный пир (класс slow или меньше половины лучшего). Проигравший турнир, но приличный пир может вернуться в следующем окне.
3. **История скорости в пуле** (`peer_best_kbps`, `peer_rot`): лучшая оценка, которую давал адрес, и число вытеснений за медленность. Порядок дозвона: сначала адреса, которые были быстрыми (+1500 к оценке при ≥ 4 МБ/с), каждый 4-й дозвон — непроверенному адресу. Быстрый в прошлом пир после сетевой ошибки набирается снова через 5 с (первые 3 раза).
4. **Snub-детектор:** пир без единого блока за 15 с при запросах в очереди сразу становится медленным и получает минимальную глубину конвейера (раньше реакция наступала только через 25 с и страйки).
5. **Жёсткий лимит:** дозвон не превышает лимит сессий с учётом дозвонов в процессе. При лимите по умолчанию это ровно таблица слотов, поведение не меняется.
6. API: `tsnx_engine_set_session_limit()` (лимит сессий торрента), `tsnx_engine_set_rotation_timing()` (интервалы, для тестов). `[perf] net`: `rotated+`, `dials+`.

### Сделано: хвосты фаз 1, 4 и 5

- **Ключ `ip:port`** (ф. 4, п. 7): пул и его хеш-индекс различают адреса по паре IP + порт, до 2 исходящих сессий на один IP. IP, с которого уже есть входящее соединение, не набирается (иначе это вторая сессия к тому же пиру). Проверено: три сида на 127.0.0.1 с разными портами — работают два, третий отсечён лимитом (раньше в пул попадал только один).
- **Пустой пул** (ф. 4, п. 9): раз в 5 с, если живых сессий меньше цели, а готовых адресов нет, — внеочередной анонс (не чаще раза в 2 минуты) и «голодный» режим DHT.
- **Повтор после таймаута дозвона** (ф. 4, п. 8): адреса от трекеров и PEX повторяются через 30 с (было 60), адреса из DHT — по-прежнему через 60 с. Повторный дозвон, как и раньше, получает таймаут 5 с.
- **Логи** (ф. 1, п. 3): «added peers», «handshake ok», «bitfield ok», «sent our bitfield» переведены в DEBUG. «incoming handshake ok» оставлен в INFO: входящих мало, а по ним видно, работает ли проброс порта. Уровень по умолчанию остался INFO, на нём выводятся строки `[perf]`.
- **`tsnx_engine_set_file_wanted()`** (ф. 5, п. 4) больше не пустышка: опережающая загрузка в конце файла (до 64 МБ следующего файла) идёт только в выбранный файл. Выбор, сделанный до открытия загрузки (при зонде), применяется при открытии. `static last_dup_dbg` стал полем торрента.
- Тесты: `test_pool.c` — фазз по `ip:port` и юнит-тест «опережающая загрузка vs выбор файлов»; `test_swarm_sched --sameip`.
